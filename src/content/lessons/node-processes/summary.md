# Процессы и потоки в Node

<details>
<summary><b>Ядро</b> — что нужно помнить</summary>

- Долгий расчёт на JS задерживает события главного потока. `await` сам по себе расчёт в другой поток не переносит.
- **worker_threads** запускает JS в другом потоке того же процесса. PID и часть ресурсов общие, но экземпляр V8, JS-куча, глобальные переменные и цикл событий свои.
- **child_process** запускает отдельную программу с собственным адресным пространством. `fork` — запуск другого Node с IPC, а не копия текущей JS-кучи.
- **cluster** создаёт такие Node-процессы и помогает обслуживать один порт несколькими копиями сервера.
- Место выполнения и способ обмена — разные решения. Между воркерами возможны клонирование, перенос буфера и общие байты. IPC между процессами сериализует данные; общей JS-памяти он не даёт.
- В показанной одноразовой задаче нужны ожидаемый ответ и успешный выход воркера. У долгоживущего воркера исход каждой задачи определяет протокол сообщений, а выход — отдельное событие.

</details>

<details>
<summary><b>Карта</b> — где какой механизм</summary>

- Два файла `main.mjs` / `sum.mjs`, `workerData`, `parentPort`, обработка ошибок и выхода — «Первый воркер».
- Свои кучи, общий пул libuv, копия `process.env` и `SHARE_ENV`, события `error` / `exit`, защита пула Buffer — «worker_threads».
- `spawn` отдаёт потоки; `execFile` буферизует вывод для колбэка; `exec` дополнительно интерпретирует строку оболочкой; `fork` добавляет IPC — «child_process».
- JSON и V8-сериализация `advanced`, ожидание ответа и завершения дочернего процесса — там же.
- Новый TCP-клиент против запросов по одному keep-alive соединению, SCHED_RR и SCHED_NONE — «cluster».
- Пулы задач — «Воркеры и параллелизм»; общая память — «Общая память и Atomics»; ограничения JS-движка — «Память в Node».

</details>

<details>
<summary><b>Подвох</b> — частые ошибки</summary>

- Ответ воркера ещё не означает успешный выход. Выход с ненулевым кодом может произойти без `error`, а выход 0 — без ожидаемого ответа.
- `events.once(worker, 'exit')` отклоняется, если раньше пришёл `error`. Для ожидания самого выхода используют отдельный обработчик `exit`.
- Обработанная ошибка JS-воркера обычно не завершает родителя. Но общее исчерпание памяти и ошибки нативного кода этой границей не изолированы.
- `spawn` без обработчика `error` может завершить родителя на ENOENT. Ненулевой код дочерней программы нужно проверять отдельно.
- Два `write` не означают два события `data`. Собранный вывод разбирают после `close`, а не `exit`; stderr тоже нужно читать.
- `fork` по умолчанию наследует стандартные потоки родителя. Для `child.stdout` нужен `silent: true` или явный `stdio`.
- JSON в IPC превращает Date в строку, Map — в `{}`. `advanced` сохраняет эти типы, но не даёт SharedArrayBuffer между процессами.
- Отдельный процесс не является песочницей с урезанными правами.

</details>

<details>
<summary><b>Детали</b> — смотреть по необходимости</summary>

- `maxBuffer` у exec/execFile по умолчанию равен 1 048 576 байтам отдельно для stdout и stderr. Переполнение — ошибка, не успешный короткий ответ.
- `markAsUntransferable` защищает общий пул маленьких Buffer от переноса; клонирование по-прежнему возможно.
- В SCHED_RR главный распределяет новые соединения с учётом доступности копий: строгое A/B не гарантируется. Все HTTP-запросы уже переданного соединения остаются у его владельца.
- Состояние cluster-копий раздельное; перезапуск должен отличать сбой от планового завершения и не создавать бесконечный цикл падений.
- Старые числа старта в теме — отдельные наблюдения на Node 26.8.2/macOS, а не универсальное соотношение цены воркера и процесса.

</details>
