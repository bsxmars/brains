  ### Два режима отвечают на разные вопросы

  По умолчанию V8 **удаляет сэмпл, когда соответствующий объект собран**. Два флага
  includeObjectsCollectedBy…GC сохраняют и такие записи. Поэтому один режим помогает искать
  продолжающие занимать память выделения, а другой — общий поток выделений, в том числе мусор.
  Оба описывают только выборку из окна записи: объект, созданный раньше её начала, сюда не попадёт.

  Название «только живое» условно: профиль без принудительной GC может содержать уже недостижимый,
  но ещё не собранный объект. В проверенной реализации CDP получение профиля запрашивает GC,
  а у v8.startHeapProfile в Node 26 параметр forceGC по умолчанию false. Формат JSON одинаков,
  но условия получения результата различаются.

  eyebrow="Раздел 2 · демо"
  eyebrowTone="demo"
  title="Цена выборки"
  lead="V8 записывает не каждое выделение. После каждого сэмпла он выбирает случайное число байт (в среднем оно равно интервалу выборки), отсчитывает столько байт новых выделений и записывает стек того выделения, на котором отсчёт закончился. Поэтому цена записи растёт с числом сэмплов, а не с числом объектов."
>
  Для потока мелких выделений полезны три приближения. Все три опираются на то, что точки выборки ставятся
  случайно: расстояние до следующей точки не зависит от прошлых и в среднем равно интервалу
  (так устроено показательное распределение):

  - сэмплов в секунду ≈ скорость выделения / интервал, если отдельные выделения много меньше интервала;
  - объект размера `s` попадает в выборку с вероятностью `1 − e^(−s/интервал)` —
    крупный почти всегда, мелкий почти никогда;
  - относительный стандартный разброс оценки байт функции — порядка `1/√n`, если её сэмплы имеют близкие веса. Это ориентир для неопределённости, не гарантия ошибки каждого профиля.

  ### Профиль выделений — не профиль процессора

  CPU-профиль ставит отметки по **времени** с заданным интервалом и записывает исполняемый стек. Профиль выделений ставит её по **байтам**. На одном прогоне стенда,
  с обоими профилями сразу, они расходятся так (Node 26.8.2, 200 000 запросов; диапазон —
  по четырём прогонам):

  В записанном прогоне `sign` занимает заметную долю CPU-профиля и не появляется в выборке выделений. А цену выделений CPU-профиль
  показывает не там, где выделяли: работа сборщика стоит отдельным кадром
  `(garbage collector)` и не привязана к функции, которая создаёт мусор. Поэтому, когда

  ### Сборки: виды и пол кучи после них

  Запись `gc` в `PerformanceObserver` несёт вид сборки в `detail.kind`: `MINOR` — быстрая
  сборка молодых объектов, `MAJOR` — полная, `INCREMENTAL` — шаг пошаговой разметки.
  Принудительный полный `gc()` в проверенном Node приходит как `MAJOR` с флагом `NODE_PERFORMANCE_GC_FLAGS_FORCED`
  в `detail.flags` — так отделяют свои принудительные сборки от настоящих.

  Для поиска накопления важно, сколько осталось **после** major GC при сопоставимой нагрузке.
  Рост может быть связан и с полезными долгоживущими данными: один тренд не доказывает утечку.
  В Node это спрашивают у `v8.GCProfiler`: он отдаёт статистику кучи до и после каждой сборки.

  ### Сравнение версий

  Сначала согласуют режим, единицы, версию рантайма, глубину стека и состав нагрузки.
  Нельзя напрямую сравнивать raw counts при разных интервалах или смешивать live и все выделения.
  Интервалы можно различать, если система корректно взвешивает байты; неопределённость
  и потеря мелких стеков при редкой выборке всё равно останутся.

  Для всех выделений полезны байты в секунду и байты на запрос. Доли показывают распределение,
  но скрывают общий рост: функция может сохранить ту же долю, выделяя вдвое больше.
  Для live-профиля смотрят оценки удерживаемых выделений при сходном состоянии GC,
  возрасте процесса и числе активных сессий. Нормирование на время записи не превращает
  live-картину в скорость выделения.

  Интервал сначала проверяют на части реплик: сравнивают задержки, CPU, память и объём выгрузки
  с контрольной группой. Отсутствие заметного замедления при 512 КБ в учебном стенде — результат
  этого опыта, а не гарантия агента. Дальше выбирают интервал и длительность так, чтобы
  интересующие функции набирали достаточно наблюдений.
</Section>

  В этом снимке без изоляции метода measureUserAgentSpecificMemory нет. Проверяют наличие
  метода через typeof; ошибки самого поддерживаемого вызова всё равно обрабатывают.
  С изоляцией один ответ пришёл через 18 секунд. Это не обещание периода или верхней задержки:
  получение результата связано с внутренними решениями браузера и GC. Частоту подбирают
  экспериментально, не используют API как синхронный датчик.

  Условия COOP/COEP и встраивания разобраны в
  [«Безопасности фронтенда», раздел «Изоляция страницы: COOP и COEP»](/platform/security/#s7).
  На этом сайте изоляция выключена.

  `performance.memory` — нестандартное поле Chromium, которое есть и без изоляции.
  По документации MDN оно устарело, а числа в нём огрублены и обновляются редко. В
  Chromium 153 `usedJSHeapSize` показал ровно 18 200 000 и не сдвинулся, пока страница
  создала ещё два миллиона объектов. С флагом `--enable-precise-memory-info` то же поле
  растёт с каждой пачкой.

  При поддержке API и выполнении требований контекста результат можно отправлять в RUM.
  performance.memory не заменяет его: это нестандартная оценка кучи V8 с ограничениями
  точности и обновления. Из неё нельзя получить всю память страницы или сопоставимый
  показатель для разных движков.
</Section>
