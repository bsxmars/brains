  `MutationObserver` собирает записи об изменениях DOM и передаёт их вместе:
  несколько вставок в одном синхронном участке не требуют отдельного вызова на каждую.

  ### Бесконечная цепочка микрозадач

  <CardGrid min={270} gap={14}>
    <Card tone="err" color="tone" gap={11}>
      <CodeBlock code={'function starve() {\n  queueMicrotask(starve);\n}'} />

      **Вкладка зависает.** Браузер перестаёт выполнять микрозадачи, только когда их очередь
      пуста, а здесь она не пустеет никогда. Страница не рисуется, не отвечает на клики,
      таймеры не срабатывают, одно ядро процессора загружено полностью.

    </Card>
    <Card tone="ok" color="tone" gap={11}>
      <CodeBlock code={'function ok() {\n  setTimeout(ok, 0);\n}'} />

      **Вкладка работает.** Колбэк ставит **задачу**, а между задачами цикл успевает
      и рисовать, и обрабатывать ввод. Вкладка живая, просто нагруженная.

    </Card>
  </CardGrid>

  Отсюда правило для долгой работы, которую режут на куски, чтобы страница не замирала: следующий
  кусок ставят **задачей** — через `setTimeout`, `MessageChannel` или `scheduler.yield()`. Тогда между
  кусками у браузера появляется возможность нарисовать кадр и обработать клик. Через `queueMicrotask` следующий кусок
  выполнится сразу, и поток так и не освободится. В Node похожее голодание вызывает рекурсивный `process.nextTick` —
  [«Цикл событий Node», раздел «Между колбэками»](/js/node-event-loop/#s3).

  ### Рендер-шаги: где живёт `requestAnimationFrame`

  Примерно раз в кадр цикл отвлекается от задач и рисует страницу. Что происходит на этом шаге —
  style, layout, paint, composite, — разобрано по шагам в теме [«Кадр браузера»](/render/render-pipeline/).

  <Plain text={PLAIN_RENDER} />

  <Card pad={22} radius={5} gap={18}>
    <FlowChips
      chips={[
        { label: 'task' },
        { label: 'микрозадачи', tone: 'info' },
        { label: 'rAF → µ', tone: 'warn' },
        { label: 'rAF → µ', tone: 'warn' },
        { label: 'style → layout → paint → composite', tone: 'ok' },
        { label: 'rIC', tone: 'dashed' },
      ]}

    **Зачем отрисовка идёт отдельным шагом.** Если бы браузер перерисовывал экран после каждого
    изменения DOM, цикл из ста `appendChild` дал бы сто пересчётов раскладки. А пользователю
    нужен один, итоговый. Поэтому изменение стиля и не видно сразу: на экран оно попадёт только
    после конца текущей задачи.

  </Card>

  <Card tone="warn" color="tone" pad="16px 18px" radius={4} size={16} lh={1.6}>

    **Чтение размеров после записи в стиль обходится дорого.** Запись только помечает
    раскладку «пересчитать потом», а чтение `offsetWidth` требует ответа сейчас — и браузер
    пересчитывает раскладку немедленно. Чередование в цикле даёт N пересчётов вместо одного
    (layout thrashing). Помогает развести их: сначала все чтения, потом все записи. Разбор
    с демо — в [«Кадр браузера», раздел «Чтение и запись»](/render/render-pipeline/#s3).

  </Card>

  <Disclosure title="Почему анимации появления используют два requestAnimationFrame">

    CSS-переход (transition) запускается, только если вычисленное значение стиля **изменилось**
    между двумя моментами, когда браузер считал стили. Только что вставленный элемент ещё
    ни разу через такой подсчёт не проходил, значит, состояния «до» у него нет. Первый `rAF`
    срабатывает в кадре, где стиль элемента ещё не считался. Второй — уже после того, как
    браузер посчитал начальное состояние. Поэтому класс `end`, добавленный во втором `rAF`,
    запускает переход.

    <CodeBlock code={"el.classList.add('start');\nrequestAnimationFrame(() =>\n  requestAnimationFrame(() => el.classList.add('end')));"} />


    Другой способ — прочитать стиль вручную: `getComputedStyle(el).opacity` заставляет браузер
    посчитать стиль сейчас, и состояние «до» тоже появляется. Двойной `rAF` надёжнее: ему
    не важно, какое свойство читать.

  </Disclosure>
</Section>

    или обработать ввод. Как работает воркер и во что обходится передача ему данных — в теме [«Воркеры
    и параллелизм»](/js/workers/).

      **Обмен только сообщениями.** `postMessage` копирует данные (структурное клонирование)
      или передаёт владение ими (transferable-объекты); отдельный путь — общая память через
      `SharedArrayBuffer` и `Atomics`. Общих объектов и общего DOM нет.

    </Card>
    <Card pad={16} radius={4} size={15.5}>

      **Сообщение от воркера — обычная задача.** Оно встаёт в очередь (источник «posted
      message») наравне с остальными и ждёт, пока главный поток освободится. Прервать главный
      поток воркер не может.

    </Card>
  </CardGrid>
</Section>
