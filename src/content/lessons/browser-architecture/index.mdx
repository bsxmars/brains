  ### Почему по сайту, а не по origin, хотя origin строже

  <Card pad={18} gap={11} size={15.5} lh={1.6}>

      Виноват старый механизм `document.domain`. Две страницы, `a.example.com`
      и `b.example.com`, могли обе присвоить `document.domain = 'example.com'`. После этого
      каждая могла **синхронно** читать и менять DOM другой.

      Если две страницы лежат в разных процессах, так не получится. Каждое чтение свойства
      превратилось бы в сообщение другому процессу и ожидание ответа (IPC), а синхронный
      код ждать не умеет. Значит, браузер обязан **заранее** положить в один процесс все страницы,
      которые могут так договориться, — то есть все страницы одного сайта.

      <CodeBlock code={'Origin-Agent-Cluster: ?1'} size={11.5} pad="11px 13px" />

      <CardNote tone="ok">

        Этим заголовком страница говорит: «группируйте меня по **origin**, `document.domain`
        мне не нужен». Заголовок меняет правило, по которому документы собираются в группу
        (кластер агентов), а для процессов это **подсказка**, не гарантия: браузер вправе
        оставить документ в процессе сайта. Chrome 153 на компьютере подсказку выполняет:
        iframe `cdn.shop.com` с `?1` внутри `app.shop.com` уезжает в отдельный процесс.

      </CardNote>

      <CardNote tone="warn">

        **Работает ли присвоение `document.domain`, решает то, как сгруппирован документ** —
        это видно по `window.originAgentCluster`. В группе по сайту (`false`) присвоение
        родительского домена проходит и меняет значение. В группе по origin (`true`) оно ничего
        не делает (no-op) — так прямо сказано в HTML Standard.

        Умолчание зависит от схемы. В Chrome 153 страница по HTTPS сгруппирована по origin
        и без всякого заголовка: `?1` ничего не меняет, а вернуть группировку по сайту — и
        работающий `document.domain` — можно только заголовком `Origin-Agent-Cluster: ?0`.
        Страница по HTTP сгруппирована по сайту всегда: вне безопасного контекста заголовок
        не действует. Присвоить чужой домен нельзя ни в каком режиме — это `SecurityError`.

        Процессы при этом раздаются по-прежнему по сайту: тот же iframe `cdn.shop.com` без
        заголовка остаётся в процессе `app.shop.com`, хотя `document.domain` ему по HTTPS
        уже недоступен.

      </CardNote>
    </Card>

  <CardGrid min={320} gap={16} align="start">
    <Card tone="err" title="Чужой HTML не отгородить поддоменом" titleSize={16.5} pad={18} gap={11} size={15.5} lh={1.6}>

      Допустим, вы раздаёте HTML, который загрузили пользователи, с `user-content.example.com`.
      Для браузера это тот же сайт, что и `app.example.com`. Правило одного источника (SOP)
      поддомены разделяет: читать чужой DOM нельзя. А **процесс у них может быть общим**:
      iframe с `user-content` внутри `app` живёт в процессе страницы, и чужой HTML лежит
      в одной памяти с вашими данными.

      <CardNote tone="err">

        Чтобы отделить процесс, нужен **другой eTLD+1** — отдельный купленный домен. Поэтому
        большие сервисы держат пользовательский контент на отдельных доменах, а не на поддомене
        основного.

      </CardNote>
    </Card>

    <Card tone="warn" color="tone" title="Где кончается сайт, решает список, а не число точек" titleSize={16.5} pad={18} gap={11} size={15.5} lh={1.6}>

      **Public Suffix List** — общий список суффиксов, под которыми домены получают разные
      владельцы. Поэтому `example.co.uk` — один сайт (`co.uk` купить нельзя), а
      `alice.github.io` и `bob.github.io` — **два разных**: `github.io` тоже в списке.

    </Card>
  </CardGrid>

  ### Изоляцию сайтов ввели после Spectre: проверки в коде перестали защищать

  <Card pad={22} gap={14} size={16.5} lh={1.6}>

    До 2018 года Chrome разводил сайты по процессам «когда получится». Iframe с чужого сайта
    жил в процессе страницы, которая его встроила. Рассуждали так: правило одного источника
    (SOP) и так запрещает читать чужой DOM, проверки стоят в каждом API — значит, данным
    разных сайтов в одном процессе ничего не грозит.

    <Card tone="info" color="tone" pad={16} radius={4} gap={9} size={15.5} lh={1.6} text={PLAIN_SPECTRE} />

    <Card tone="err" color="tone" pad="15px 17px" radius={4} gap={11} size={16} lh={1.6}>

      Процессор выполняет команды наперёд, ещё не зная, понадобятся ли они (спекулятивное
      исполнение). Так можно **прочитать память своего процесса в обход проверок в API**:
      проверка написана в коде, а процессор забегает вперёд раньше неё. По шагам:

      <NumberedList items={SPECTRE_STEPS} />

      <CardNote tone="err">

        Последний шаг держится на точном таймере: разница между строкой из кэша и строкой
        из памяти — десятки наносекунд. Поэтому браузеры огрубили `performance.now()`
        и отобрали `SharedArrayBuffer` — из общего счётчика в соседнем потоке получается
        самодельный точный таймер.

      </CardNote>
    </Card>

    <Callout size={18} pad="16px 18px">

      Значит, единственная надёжная граница — не проверка, а <b>адресное пространство</b>.
      Если чужие данные не должны быть прочитаны — их не должно быть в этом процессе.

    </Callout>


    **Развести сайты по процессам мало.** Чужие данные можно затащить в свой процесс вполне
    законно. Тег `<img src="https://bank.com/api/accounts.json">` ничего не нарисует, но байты
    ответа окажутся в памяти процесса атакующей страницы, а Spectre этого достаточно. Поэтому
    ответы фильтрует сетевой процесс (network service), механизм называется CORB, а теперь ORB.
    Если ответ похож на данные, а запросила его без CORS (разрешения, которым сервер
    открывает свой ответ чужим страницам) страница чужого сайта, тело ответа до неё
    не доходит вовсе.

    <Card tone="ok" color="tone" pad="15px 17px" radius={4} size={16} lh={1.6}>

      **Что сделать у себя:** отдавайте ответы API с правильным
      `Content-Type: application/json` и с `X-Content-Type-Options: nosniff`. Иначе фильтр
      не поймёт, что это данные, и защита не сработает.

    </Card>
  </Card>

  ### Изоляция по источнику: `SharedArrayBuffer`, COOP и COEP

  <Card tone="warn" color="tone" title="Почему `SharedArrayBuffer` на этом сайте нет даже как имени" titleSize={17} pad={20} gap={12} size={15.5} lh={1.6}>
    <Card tone="info" color="tone" pad={16} radius={4} gap={9} size={15.5} lh={1.6} text={PLAIN_ISOLATION} />

    Память, общую для нескольких потоков, браузер выдаёт только странице, **изолированной
    по источнику**. Изоляцию включают два заголовка ответа сервера.
    `Cross-Origin-Opener-Policy: same-origin` разрывает связь с окнами, которые открыли вас
    или которые открыли вы: для одной ссылки то же делает `rel="noopener"`, а здесь — для
    всего документа. `Cross-Origin-Embedder-Policy: require-corp` требует, чтобы каждый подключённый
    ресурс явно разрешил встраивать себя.

    Получив оба заголовка, браузер ставит `crossOriginIsolated` в `true` и открывает три
    возможности: `SharedArrayBuffer`, точный (не огрублённый) `performance.now()`
    и `performance.measureUserAgentSpecificMemory()`. Ровно те, что отобрали после Spectre:
    теперь страница доказала, что чужих данных без их согласия в её процессе нет. Изоляция
    сайтов по процессам этого не заменяет — она работает и без заголовков, а возможностей
    не возвращает.

    На этом сайте нет ни одного из них: сайт собран в статические файлы и таких заголовков
    не отдаёт. Поэтому `crossOriginIsolated` здесь `false`, а `SharedArrayBuffer`
    **отсутствует как имя**. Не «есть, но запрещён», а нет вовсе.

    <CardNote tone="err">

      Что из этого следует для кода: привычная обёртка `try { new SharedArrayBuffer(1) } catch`
      ловит здесь **не то**. Она поймает `ReferenceError` — «такого имени нет», а не отказ
      в правах. Проверять надо `self.crossOriginIsolated`, а затем
      `typeof SharedArrayBuffer === 'undefined'`.

    </CardNote>

    <CardNote tone="ok">

      `Atomics` при этом на месте: объект есть и без изоляции, просто ему не с чем работать.
      А `Atomics.wait` в главном потоке бросает `TypeError` при любой изоляции. Это отдельный
      запрет, с заголовками он не связан: главный поток нельзя остановить ожиданием.

    </CardNote>
  </Card>
</Section>

  ### Как Chrome раздаёт процессы: `process-per-site-instance` и `process-per-site`

  <Card pad={20} gap={12} size={15.5} lh={1.6}>

    По умолчанию Chrome работает в режиме **`process-per-site-instance`**. SiteInstance — это
    группа документов одного сайта, которые могут дотянуться друг до друга. Например, главный
    фрейм, его iframe с того же сайта и окно, открытое из него без `noopener`. Каждая такая
    группа получает свой процесс. Поэтому две вкладки одного сайта, открытые **независимо**, —
    это две SiteInstance и, как правило, два процесса. (BrowsingInstance — группа пошире: все
    окна и фреймы, связанные через `opener` и родителя, с любых сайтов.)

    **`process-per-site`** устроен иначе: все документы одного сайта во всём браузере делят
    один процесс, кто бы кого ни открыл. Chrome включает его только для своих служебных
    страниц и расширений, а как режим запуска он нужен для отладки. Есть и два крайних режима:
    `process-per-tab` и `single-process`. Последний ломает ту самую гарантию, ради которой всё
    построено, и существует только для отладки.

    <CardNote tone="warn">

      Модель обещает, что **разные сайты** не окажутся вместе, а не что каждая вкладка получит
      свой процесс. Упёршись в лимит процессов, Chrome кладёт новую SiteInstance в уже
      работающий процесс того же сайта, но никогда — в процесс чужого.

    </CardNote>
  </Card>

  ### Песочницу строят в расчёте на то, что рендерер уже захвачен

  <Card tone="err" pad={22} gap={14} size={16.5} lh={1.6}>

    Исходное допущение: атакующий уже выполняет любой свой машинный код внутри рендерера.
    Задача песочницы — чтобы оттуда он не мог сделать ничего полезного для себя.

    <CardGrid min={230} gap={10}>
      {SANDBOX_CANNOT.map((item) => (
        <Card tone="err" pad={13} radius={4} size={15} lh={1.55} color="tone">

          ✗ {item}

        </Card>

    На каждой операционной системе песочница устроена по-своему: seccomp-bpf на Linux, Seatbelt
    на macOS, ограниченный токен и AppContainer на Windows. Названия запоминать незачем. Важно
    общее правило: **список разрешённых операций короткий и задан заранее.**

    <Callout size={17.5} pad="16px 18px">
      <b>Процесс браузера не доверяет рендереру ни в чём.</b> Каждое сообщение он проверяет так,
      будто его прислал злоумышленник, — потому что, возможно, так и есть. Рендерер,
      закреплённый за сайтом A, получает отказ на любой запрос, касающийся сайта B.

    </Callout>


    Поэтому для взлома Chrome всегда нужны минимум два бага. Первый даёт выполнить свой код
    в рендерере (RCE). Второй — **побег из песочницы** (sandbox escape) — это ошибка в том,
    как процесс браузера принимает сообщения от рендерера. Отсюда и правило: таких точек входа (интерфейсов
    Mojo) держат как можно меньше. А изоляция сайтов полезна даже без побега: с одним первым
    багом атакующему достаются данные только одного сайта.

  </Card>

    Страница вызывает `window.open('/report')`, и отчёт открывается на том же сайте. Новая
    вкладка попадает в ту же BrowsingInstance и ту же SiteInstance. Значит, и в тот же процесс,
    и на тот же главный поток, и в тот же агент — с одним циклом событий на двоих. Тяжёлый
    расчёт в отчёте подвешивает исходную страницу.

    <Card tone="ok" color="tone" pad="15px 17px" radius={4} size={16} lh={1.6}>

      `rel="noopener"` разрывает связь: новое окно попадает в новую BrowsingInstance и, скорее
      всего, в другой процесс. Обычно его советуют ради безопасности: чтобы открытая вкладка
      не могла подменить адрес исходной (tabnabbing). Но есть и второй эффект, о котором почти
      не говорят: **тяжёлая вкладка перестаёт тормозить исходную**. Ссылке с `target="_blank"`
      он больше не нужен: с Chrome 88, Firefox 79 и Safari 12.1 она подразумевает `noopener`
      сама. Связь сохраняет только `window.open`.

    </Card>

    <Card tone="warn" color="tone" pad="15px 17px" radius={4} size={16} lh={1.6}>

      **Зеркальная ловушка:** две вкладки одного сайта, открытые независимо, лежат в разных
      BrowsingInstance. У них разные агенты и разные циклы событий. Но из-за повторного
      использования процессов они могут оказаться в **одном процессе**. Тогда по спецификации
      циклы событий у них разные, а главный поток физически один. Спецификация и реализация
      здесь расходятся; рассчитывайте на худший случай.

    </Card>
  </Card>

  <Card title="`window.top` и `parent` остаются, а синхронного доступа нет" titleSize={18} pad={22} gap={14} size={16.5} lh={1.6}>

    Фрейм в отдельном процессе (OOPIF) не теряет ссылок на другие окна. `window.parent`,
    `window.top`, `frames[0]` и `window.length` во фрейме с чужого сайта работают так же, как
    в своём. Пропадает другое — всё, для чего нужно **прочитать чужую память прямо сейчас**.
    `parent.document` бросает `SecurityError`, чтение `top.location.href` тоже, а до DOM, стилей
    и геометрии родителя не добраться вовсе.

    Осталось немногое, и выбрано оно не случайно: `postMessage`, `closed`, `focus`, `blur`,
    `close`, `frames`, `length`, `opener`, `parent`, `top` и **запись** в `location`. Ни одной
    из этих операций не нужно синхронно заглядывать в другой процесс. Сообщение уходит
    асинхронно, переход по адресу — это просьба к браузеру, а число фреймов известно и своей
    стороне.

    <Callout size={17.5} pad="16px 18px">
      <b>Это не два правила, а одно.</b> Синхронный доступ заканчивается там же, где процесс.
      Иначе вынести фрейм в другой процесс было бы нельзя: каждое чтение чужого DOM превратилось
      бы в сообщение другому процессу с ожиданием ответа.

    </Callout>
  </Card>
