<Section
  id="basics"
  eyebrow="Основа"
  title="Как это выглядит в коде"
  lead="`new MessageChannel()` возвращает два связанных порта, `port1` и `port2`. Что отправили в один, приходит в другой, и в обратную сторону тоже."
>

  Отправляют методом `postMessage(данные)`, принимают обработчиком `onmessage`: данные лежат
  в `event.data`. Важно направление: `port1.postMessage(…)` отправляет **из** `port1`,
  и сообщение приходит на противоположный конец, в `port2`. Поэтому первым в консоли пишет
  `port2`, а ответ, отправленный из `port2`, приходит в `port1`. Получатель видит копию,
  а не тот же объект: менять её можно, у отправителя ничего не поменяется. `close()` на любом конце закрывает канал целиком.

  <Card label="один канал внутри страницы" labelSize={12} pad={18} radius={5} gap={11}>
    <CodeBlock code={BASICS_CHANNEL_CODE} size={11.5} />
  </Card>

  <Card label="в консоли" labelSize={12} pad={18} radius={5} gap={11}>
    <CodeBlock code={BASICS_CHANNEL_OUT} size={11.5} />
  </Card>

  Внутри одной страницы канал не нужен: функцию проще вызвать напрямую. Он нужен, когда один
  из портов уезжает в воркер или iframe. Порт отдают через `postMessage` того, кто уже на связи,
  и перечисляют его во втором аргументе — списке переноса. После этого у страницы и воркера
  своя отдельная линия, и её сообщения не смешиваются с остальными.

    <Card label="worker.js" labelSize={12} pad={18} radius={5} gap={11}>
      <CodeBlock code={BASICS_WORKER_CODE} size={11.5} />
    </Card>
  </CardGrid>

  Подписаться можно и через `addEventListener`, но тогда в браузере порт нужно запустить
  вызовом `start()`. Присваивание `onmessage` запускает порт само, `addEventListener` — нет:
  без `start()` сообщения будут копиться и не придут. Как это выглядит и чем отличается
  Node — в разделе «Жизненный цикл порта».

      **`close()` разрывает связь с обеих сторон.** После этого `postMessage` с другой стороны
      молча ничего не делает — без исключения. Сообщения «канал закрыт» не будет.

    </Card>
    <Card tone="err" pad={16} radius={4} size={15.5}>

      **После передачи ваш объект порта становится пустым (detached).** `postMessage`,
      `start()` и `close()` на нём ничего не делают и не бросают ошибку. Эта тихая потеря сообщений — частая причина жалобы
      «половина событий не доходит».

    </Card>
    <Card tone="ok" color="tone" pad={16} radius={4} size={15.5}>

      **Накопление до передачи — полезный приём.** Можно писать в порт до того, как второй конец
      кто-то получил. Ничего не потеряется, порядок сохранится. Это убирает целый класс гонок
      вида «воркер ещё не подписался, а мы уже шлём».

    </Card>
  </CardGrid>

  <Card
    tone="warn"
    title="Частая ошибка: `addEventListener` не запускает порт, а `onmessage` запускает"
    titleSize={17}
    pad={20}
    radius={5}
    gap={13}
  >
    ```js
    port.addEventListener('message', fn);   // сообщения копятся, но не приходят
    port.start();                           // ← без этой строки тишина

    port.onmessage = fn;                    // а вот это стартует порт неявно
    ```

    По спецификации очередь включается, когда `onmessage` присваивают в первый раз.
    У `addEventListener` такого побочного эффекта нет. Отсюда классический баг: «переписал
    на `addEventListener` ради `{ once: true }` — и всё молча сломалось».

    <Card tone="err" color="tone" pad="15px 17px" radius={4} size={16} lh={1.6}>

      **В Node поведение другое:** `addEventListener('message')` сам стартует порт, и сообщение
      приходит без единого вызова `start()`. Значит, код, который проходит тесты в Node, может
      молча не работать в браузере. Вызывайте `start()` всегда: повторный вызов безвреден.

    </Card>
  </Card>

  ### `close()` и сборка мусора

  <Card tone="err" title="Незакрытый порт — это утечка, и немаленькая" titleSize={18} pad={22} radius={5} gap={14}>

    Спецификация HTML не даёт сборщику мусора удалить порт, пока у него есть что доставить,
    а связанный порт держится так, будто на него ссылается напарник. Chromium и Node идут
    дальше и не трогают порт, который просто слушает: вдруг придёт сообщение. Значит, **живой
    слушающий порт — это корень для сборщика (GC root)**: он держит в памяти замыкание
    обработчика и всё, что оно захватило.

    <Plain text={PLAIN_GC_ROOT} />

    <FlowChips
      minWidth={0}
      chips={[
        { label: 'port1 (root)' },
        { label: 'замыкание onmessage' },
        { label: 'что захватило замыкание' },
        { label: 'например, компонент со всем деревом', tone: 'info' },
      ]}
    />


    Лечится вызовом `close()`, и он должен стоять на **каждом** пути выхода: успех, ошибка,
    таймаут, `abort`, размонтирование компонента, `pagehide`. `WeakRef` и `FinalizationRegistry`
    тут не помогут: они срабатывают, когда объект стал недостижим, а слушающий порт таким
    не становится. Почему корень держит под собой всё поддерево
    и как такую утечку находят в снимке кучи — в [теме про память и сборщик](/js/memory-gc/).

    <Card tone="err" color="tone" pad="15px 17px" radius={4} size={15.5} lh={1.6}>

      **Отсюда жалоба Jest «did not exit» в связке с jsdom.** Планировщик React сначала
      пробует `setImmediate` и только без него создаёт `MessageChannel` — и никогда его
      не закрывает. В чистом Node `setImmediate` есть, и канала нет. А `jest-environment-jsdom`
      `setImmediate` не даёт, и планировщик открывает канал. Что именно держит процесс, покажет
      `--detectOpenHandles`.

    </Card>
  </Card>
</Section>

<Section
  id="s2"
  eyebrow="Раздел 2"
  title="Чем отдать поток: `setTimeout` против сообщения порта"
  lead="Планировщику нужно «дай браузеру нарисовать кадр и сразу вернись к работе». А `setTimeout`, вызванный из `setTimeout` глубже пяти уровней, по стандарту HTML превращается в паузу 4 мс, даже если просили ноль."
>

  Допустим, список из десяти тысяч строк строится одной задачей за 200 мс — и все 200 мс
  клик по кнопке ждёт. Лечение — резать работу на порции по несколько миллисекунд и между порциями отдавать
  поток. Весь вопрос в том, чем отдавать.

  <Plain text={PLAIN_YIELD} />

  <Card title="Планировщик на сообщениях порта" titleSize={17} pad={20} radius={5} gap={13} size={16} lh={1.6}>
    <CodeBlock code={SCHEDULER_CODE} size={12} />

    Это сокращённая версия `scheduler/src/forks/Scheduler.js` из React: 5 мс работы, потом
    пауза, чтобы браузер нарисовал кадр. Каждое сообщение — отдельная задача, поэтому между двумя порциями
    браузер успевает обработать клик и нарисовать кадр. Зачем React это делает и что он режет
    на куски — в [теме про ре-рендеринг](/frameworks/react-rerender/#s4).

    **Флаг `scheduled` склеивает повторные вызовы.** Пока сообщение уже в пути, новый
    `schedule()` ничего не отправляет: работа лежит в `queue`, и её заберёт та же задача.
    Без флага десять вызовов подряд дали бы десять сообщений. Девять из них пришли бы
    к пустой или почти пустой очереди и потратили оборот цикла впустую. Флаг сбрасывается
    в начале обработчика: если за время порции кто-то добавил работу, следующий
    `schedule()` снова отправит сообщение.

  </Card>

  <Card tone="dim" color="tone" pad="16px 18px" radius={4} size={16} lh={1.6}>

    **Канал — не единственный способ отдать поток, и уже не лучший.** Микрозадача поток
    не отпускает вовсе, `setTimeout` отпускает, но платит паузой в 4 мс. `scheduler.postTask`
    даёт то, чего у канала нет, — приоритет и отмену, а `scheduler.yield()` ставит продолжение
    в начало очереди, а не в конец. Канал остаётся
    запасным путём там, где планировщика нет. Сравнение всех способов, их потолки и запасной
    путь через `globalThis` — в теме про планирование задач, раздел
    [«Чем возвращать управление циклу»](/js/task-scheduling/#s1).

  </Card>

  ### А вот и замер — и он говорит про Node кое-что неожиданное

  Отдать поток — значит прервать свою работу, дать циклу событий заняться другими делами
  и продолжить потом. Как проверить, что способ действительно отдаёт поток? По цене не
  понять: самый дешёвый способ может не отдавать его вовсе. Поэтому рядом запускают
  счётчик, который растёт, только когда цикл переходит к следующему обороту. Потом тысячу
  раз отдают поток проверяемым способом и смотрят, насколько счётчик вырос.

  <CardGrid min={280} gap={14}>
    <Card pad={16} radius={4} size={15.5}>

      **`SharedArrayBuffer` не передаётся, а клонируется** — и обе стороны получают доступ
      к одной и той же памяти. Но отправить его можно только со страницы с изоляцией источника
      (cross-origin isolated: заголовки `COOP` + `COEP`), иначе `DataCloneError`. Как ждать
      и будить друг друга через `Atomics` — [«Общая память и Atomics», раздел «Ждать
      и будить»](/js/atomics/#s5).

    </Card>
    <Card pad={16} radius={4} size={15.5}>

      **Клон — тот же алгоритм, что у `structuredClone`.** Проходят `Date`, `RegExp`, `Map`,
      `Set`, TypedArray, `Error`, `BigInt`, циклы. Функции, DOM-узлы и `Proxy` бросают
      `DataCloneError` — прокси, сколько бы обычных полей ни было у цели. А символьные ключи,
      прототип, `#`-поля и геттеры класса пропадают молча; собственный геттер объекта
      срабатывает, и уезжает его значение. Отсюда «обычный объект уходит, а состояние падает»:
      `reactive()` во Vue — это прокси, и перед отправкой ему нужен `toRaw()`. Без канала тот же
      клон делает `structuredClone(value)`, а с `{ transfer: [buf] }` — и перенос. Что именно
      теряется на клонировании — [«Копирование и сериализация», раздел «Structured clone
      по шагам»](/js/serialization/#s4); почему прототип,
      приватные поля и геттеры ведут себя именно так — в [объектной модели](/js/object-model/).

    </Card>

    «Циклы проходят» — за этой строчкой стоит механизм. Алгоритм обходит граф объектов
    не наивно: он ведёт **карту уже склонированных объектов**. Встретив ссылку, он сначала смотрит в карту,
    и если объект там уже есть — подставляет готовый клон вместо того, чтобы делать второй.

    Отсюда два следствия. `a.self = a` не уводит обход в бесконечность: на втором заходе `a`
    уже в карте. И идентичность внутри одного сообщения сохраняется — если один и тот же объект
    лежит в двух полях, на той стороне это снова будет **один** объект, а не две копии.
    `JSON.parse(JSON.stringify(x))` не умеет ни первого, ни второго: на цикле он падает,
    а общий объект раздваивает.

    <CardNote tone="prose">

      Карта живёт ровно одно сообщение. Два `postMessage` подряд с одним и тем же объектом
      дадут на приёме два независимых объекта — между сообщениями идентичность не переносится.

    </CardNote>
  </Card>

  <Card title="Переносится — это не то же самое, что клонируется" titleSize={17} pad={20} radius={5} gap={13}>

    Два независимых свойства, и объект может иметь любое из них, оба или ни одного. `ImageBitmap`
    и **клонируется**, и переносится. `OffscreenCanvas` — только переносится: холст один, копии
    у него быть не может по смыслу. В Node так же устроен `FileHandle`.

    <CardNote tone="prose">

      Переносятся в браузере: `ArrayBuffer`, `MessagePort`, `ReadableStream` / `WritableStream` /
      `TransformStream`, `ImageBitmap`, `OffscreenCanvas`, `RTCDataChannel`, `AudioData` /
      `VideoFrame`, `MediaSourceHandle`.

    </CardNote>
  </Card>
</Section>

<Section id="s4" eyebrow="Раздел 4" title="Применение" lead={APPLY_LEAD}>
  <Card title="Приватный канал с iframe: владение портом вместо проверки origin" titleSize={18} pad={22} radius={5} gap={16}>
    <CardGrid min={270} gap={16}>
      <Card tone="err" label="window.postMessage" labelTone="tone" labelSize={11} pad={16} radius={5} gap={9}>

        На **каждом** сообщении надо проверять `event.origin` и `event.source`, иначе любой, кто
        добрался до ссылки на окно, шлёт вам что хочет.

      </Card>
      <Card tone="ok" color="tone" label="порт" labelTone="tone" labelSize={11} pad={16} radius={5} gap={9}>

        Origin проверяется **один раз, в рукопожатии**. Дальше сам канал и есть право на общение.

      </Card>
    </CardGrid>

    ```js
    // parent: ждём загрузки фрейма — до неё origin не совпадёт, и порт пропадёт
    iframe.addEventListener('load', () => {
      const { port1, port2 } = new MessageChannel();
      port1.onmessage = ({ data }) => handle(data);    // отправителя проверять уже не нужно
      iframe.contentWindow.postMessage({ type: 'init' }, 'https://widget.example', [port2]);
    });

    // iframe
    addEventListener('message', function onInit(e) {
      if (e.origin !== 'https://app.example') return;   // ← единственная проверка
      if (e.data?.type !== 'init') return;              // чужое сообщение — ждём дальше
      removeEventListener('message', onInit);           // своё — дальше только через порт
      const port = e.ports[0];
      port.onmessage = ({ data }) => port.postMessage(process(data));
    });
    ```

    <Card tone="warn" color="tone" pad="15px 17px" radius={4} size={16} lh={1.6}>

      Точный целевой origin (не `'*'`) обязателен: звёздочка отдаст порт любому, кто успел
      загрузиться в этот фрейм. **Порт — это передача полномочия, отдавать его вслепую нельзя.**

    </Card>
  </Card>

  <CardGrid min={300} gap={16} align="start">
    <Card title="Удалённый вызов: одноразовый порт на вызов" titleSize={16.5} pad={18} radius={5} gap={11}>

      Удалённый вызов (RPC) — вызвать функцию на той стороне и дождаться ответа. Отдельный
      порт на каждый вызов проще, чем сопоставлять ответы с запросами по id, и не нужно чистить
      таблицу ожидающих вызовов.

      ```js
      function call(port, method, args) {
        const { port1, port2 } = new MessageChannel();
        const answer = new Promise((resolve, reject) => {
          const timer = setTimeout(() => {   // ← обязательно
            port1.close();
            reject(new Error('rpc timeout'));
          }, 5000);
          port1.onmessage = ({ data }) => {
            clearTimeout(timer);
            port1.close();
            data.ok ? resolve(data.value) : reject(data.value);
          };
        });
        port.postMessage({ method, args, reply: port2 }, [port2]);
        return answer;
      }
      ```

      `close()` в обеих ветках — не аккуратность, а обязательное условие: слушающий порт —
      корень для сборщика мусора (см. «`close()` и сборка мусора»), и без закрытия канал
      останется в памяти вместе со всем, что захватил обработчик. `clearTimeout` после ответа
      нужен по той же причине: таймер иначе ещё пять секунд держит замыкание, а в Node — и сам
      процесс.

    </Card>

    <Card title="Один воркер — много независимых каналов" titleSize={16.5} pad={18} radius={5} gap={11}>
      ```js
      const worker = new Worker('/worker.js');

      function openChannel(name) {
        const { port1, port2 } = new MessageChannel();
        worker.postMessage({ open: name, port: port2 }, [port2]);
        return port1;      // своя фича — свой порт и свой протокол
      }
      const search = openChannel('search');
      const parse  = openChannel('parse');

      // worker.js: каждой фиче — свой обработчик на своём порту
      self.onmessage = ({ data }) => {
        if (data.open) handlers[data.open](data.port);
      };
      ```

      Вместо одного `switch` по `data.type` на всё приложение. Плюс изоляция: чтобы закрыть
      одну фичу, хватит `close()` её порта, остальные не пострадают.

    </Card>

    <Card tone="warn" title="ServiceWorker: запрос-ответ вместо «крикнул в пустоту»" titleSize={16.5} pad={18} radius={5} gap={11}>
      ```js
      function ask(msg) {
        const { port1, port2 } = new MessageChannel();
        return new Promise((resolve, reject) => {
          const timer = setTimeout(() => { port1.close(); reject(new Error('sw timeout')); }, 3000);
          port1.onmessage = ({ data }) => { clearTimeout(timer); port1.close(); resolve(data); };
          navigator.serviceWorker.controller?.postMessage(msg, [port2]);
        });
      }
      ```

      Здесь таймаут обязателен. `controller` может быть `null` — например, при первой загрузке
      страницы, пока воркер её ещё не контролирует. А браузер может остановить ServiceWorker
      посреди обработки, если тот ждёт чего-то без `event.waitUntil`. В обоих случаях ответа
      не будет никогда, и никакого события об этом тоже.

    </Card>

    <Card tone="info" title="Node: синхронный вызов в воркер" titleSize={16.5} pad={18} radius={5} gap={11}>

      Node умеет **синхронно** снять сообщение с порта, не дожидаясь цикла событий; в браузере
      такой функции нет вовсе. На этом построены библиотеки синхронного удалённого вызова
      и хуки загрузчика модулей из `module.register()`: они работают в отдельном потоке, а Node
      ждёт их ответа синхронно.

      ```js
      import { Worker, MessageChannel, receiveMessageOnPort } from 'node:worker_threads';

      const shared = new Int32Array(new SharedArrayBuffer(4));   // флаг, видный обоим потокам
      const { port1, port2 } = new MessageChannel();
      new Worker('./worker.js', { workerData: { shared, port: port2 }, transferList: [port2] });

      function syncCall(payload) {
        Atomics.store(shared, 0, 0);
        port1.postMessage(payload);
        Atomics.wait(shared, 0, 0);       // блокируем поток
        return receiveMessageOnPort(port1).message;
      }
      ```

      ```js
      // worker.js: port — второй конец канала, shared — тот же Int32Array
      import { workerData } from 'node:worker_threads';
      const { shared, port } = workerData;

      port.on('message', (payload) => {
        port.postMessage(handle(payload));   // 1) сначала ответ в порт
        Atomics.store(shared, 0, 1);         // 2) потом флаг
        Atomics.notify(shared, 0);           // 3) и только теперь будим
      });
      ```

      Порядок в воркере важен: сначала `postMessage`, потом `notify`. Иначе главный поток
      проснётся раньше, чем сообщение попадёт в очередь, и `receiveMessageOnPort` вернёт
      `undefined`. В браузере это не повторить: `Atomics.wait` на главном потоке запрещён,
      а `receiveMessageOnPort` там просто нет.

    </Card>
  </CardGrid>

  ### `SharedWorker`: порт — единственный вход

  Выделенный воркер принадлежит одной вкладке, `SharedWorker` — всем вкладкам одного
  источника сразу. Своего `postMessage` у него нет: вкладка получает порт `worker.port`,

  ### `BroadcastChannel`: тот же обмен, но без портов

  Ближайший сосед `MessageChannel` устроен иначе. Пары концов здесь нет. В каждой вкладке,
  окне или воркере одного источника создают `new BroadcastChannel(имя)` с одним и тем же
  именем. Сообщение получают **все** объекты с этим именем, кроме того, через который его
  отправили.

  ```js
  // в каждой вкладке
  const bc = new BroadcastChannel('auth');
  bc.onmessage = ({ data }) => {
    if (data.type === 'logout') location.assign('/login');
  };

  // во вкладке, где нажали «выйти»
  bc.postMessage({ type: 'logout' });   // придёт всем, кроме себя
  ```

  <CardGrid min={280} gap={14}>
    <Card pad={16} radius={4} size={15.5}>

      **Полномочия нет.** Порт — ключ, который отдают одному адресату. Имя канала знает любой
      код того же источника, и подписаться может любой. Граница здесь — источник, а не владение.

    </Card>
    <Card pad={16} radius={4} size={15.5}>

      **Transfer-списка нет.** `postMessage` принимает один аргумент, остальное молча
      игнорируется: буфер уедет копией, а у отправителя останется целым. Функция в сообщении
      бросает `DataCloneError` сразу, у отправителя.

    </Card>
    <Card tone="warn" color="tone" pad={16} radius={4} size={15.5}>

      **Ни адресата, ни ответа.** Выбрать, кому писать, нельзя, и ответа не дождаться. Поэтому
      запрос-ответ на нём не строят. Его берут там, где нужно «сообщить всем вкладкам». Если
      нужно, чтобы работу сделала **одна** вкладка, проще взять замок Web Locks
      (`navigator.locks.request(имя, fn)`: держать его может только одна вкладка), чем выбирать
      главную вкладку через канал вручную.

    </Card>
  </CardGrid>
