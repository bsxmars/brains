# Миграции базы без простоя

`delivery/db-migrations` · выжимка составлена с ИИ 2026-10-29 по тексту темы. Ключ ответа: сначала расскажи тему сам за 2 минуты, не глядя, потом открывай.

<details>
<summary><b>Ядро</b> — что нужно помнить</summary>

- **Что это:** смена схемы базы так, чтобы текущие версии и допустимый откат оставались совместимыми со схемой, а ожидание и удержание блокировок были ограничены.
- **Зачем:** выкат идёт по частям, схема одна на все поды — несколько минут на ней работают старая и новая версии, а при откате старая снова встречает новую схему.
- **Как работает:** изменение раскладывают на расширение схемы, совместимый код, перенос и проверку данных, затем отдельное удаление. На каждом шаге проверяют запросы всех допустимых версий и цену блокировок.

</details>

<details>
<summary><b>Карта</b> — знать, что это существует</summary>

- Добавление nullable-столбца обычно переживается старым кодом; новые ограничения могут сломать INSERT. Удаление и переименование требуют согласования с кодом → «раздел Две версии на одной базе».
- Переименование: новый столбец и BEFORE-триггер до v2; перенос после ухода v1; закрыть откат на v1 и снять триггер до v3; старый столбец удалить отдельно → «раздел Расширить и сузить».
- Мгновенный `ALTER` ждёт самую долгую транзакцию, а за ним в очередь встают все запросы → «раздел Блокировки».
- Три вопроса к `ALTER`: какая блокировка, есть ли перезапись, читает ли таблицу целиком → «раздел Перезапись и проходы».
- Обязательность через `NOT VALID` + `VALIDATE`, индекс через `CONCURRENTLY` → «раздел Перезапись и проходы».
- Перенос короткими пачками по диапазону ключа, с явно заданным afterBatch для пауз и регулирования нагрузки → «раздел Перенос пачками».
- Откат кода и обратная миграция — разные действия → «раздел Откат».

</details>

<details>
<summary><b>Подвох</b> — крайние случаи и частые ошибки</summary>

- `RENAME COLUMN` быстрый, но для старого кода это удаление столбца.
- Перенос, пока работает старая версия: строки без нового столбца и молча устаревшие значения (план синхронизирует каждую запись v1 триггером; одного ожидания ухода v1 недостаточно для исправления уже устаревших непустых значений).
- Упавший `CREATE INDEX CONCURRENTLY` оставляет невалидный индекс; `DEFAULT now()` даёт всем старым строкам одно время.

</details>

<details>
<summary><b>Детали</b> — не учить, смотреть в теме</summary>

- Коды: `42703` нет столбца, `23502` обязательный пуст, `23514`, `55P03` → «раздел Две версии на одной базе».
- Режимов блокировок восемь; почти любой `ALTER` берёт `ACCESS EXCLUSIVE` → «раздел Блокировки».
- `lock_timeout` и `statement_timeout` по умолчанию 0 — ждать вечно → «раздел Блокировки».
- Перезапись: `integer`→`bigint`, `text`→`varchar(320)`, `DEFAULT gen_random_uuid()` → «раздел Перезапись и проходы».
- На снимке PGlite один UPDATE дал рост ×2,37; пачки с VACUUM — ×1,48. Это не универсальный коэффициент → «раздел Перенос пачками».
- Миграцию — Job или хук `pre-upgrade`, не при старте пода → «раздел Откат».

</details>
