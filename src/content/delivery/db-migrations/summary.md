# Миграции базы без простоя

`delivery/db-migrations` · выжимка составлена с ИИ 2026-10-29 по тексту темы. Ключ ответа: сначала расскажи тему сам за 2 минуты, не глядя, потом открывай.

<details>
<summary><b>Ядро</b> — что нужно помнить</summary>

- **Что это:** смена схемы базы так, чтобы ни одна работающая версия кода не падала и таблица не стояла закрытой дольше миллисекунд.
- **Зачем:** выкат идёт по частям, схема одна на все поды — несколько минут на ней работают старая и новая версии, а при откате старая снова встречает новую схему.
- **Как работает:** миграцию запускают один раз до выката → опасную правку раскладывают на безопасные шаги («расширить и сузить») → каждую команду пишут с мягкой блокировкой и `lock_timeout` → необратимый шаг откладывают.

</details>

<details>
<summary><b>Карта</b> — знать, что это существует</summary>

- Добавлять безопасно, убирать и переименовывать — нет → «раздел Две версии на одной базе».
- Переименование: новый столбец, три версии кода, перенос, удаление старого отдельным выкатом → «раздел Расширить и сузить».
- Мгновенный `ALTER` ждёт самую долгую транзакцию, а за ним в очередь встают все запросы → «раздел Блокировки».
- Три вопроса к `ALTER`: какая блокировка, есть ли перезапись, читает ли таблицу целиком → «раздел Перезапись и проходы».
- Обязательность через `NOT VALID` + `VALIDATE`, индекс через `CONCURRENTLY` → «раздел Перезапись и проходы».
- Перенос короткими пачками по диапазону ключа, с паузами для `VACUUM` → «раздел Перенос пачками».
- Откат кода и обратная миграция — разные действия → «раздел Откат».

</details>

<details>
<summary><b>Подвох</b> — крайние случаи и частые ошибки</summary>

- `RENAME COLUMN` быстрый, но для старого кода это удаление столбца.
- Перенос, пока работает старая версия: строки без нового столбца и молча устаревшие значения (нужен триггер или ждать ухода `v1`).
- Упавший `CREATE INDEX CONCURRENTLY` оставляет невалидный индекс; `DEFAULT now()` даёт всем старым строкам одно время.

</details>
