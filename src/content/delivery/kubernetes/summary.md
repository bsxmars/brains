<details>
<summary><b>Ядро</b> — что нужно помнить</summary>

- **Что это:** система, которая сводит желаемое с действительным: вы описываете, каким должно быть приложение, контроллеры раз за разом сравнивают и делают по шагу.
- **Зачем:** упавшее возвращается само, версия меняется волнами без остановки сервиса, откат — тот же механизм.
- **Как работает:** Deployment заводит новый ReplicaSet → ReplicaSet держит число подов → планировщик выбирает узел по `requests`, kubelet запускает контейнеры и пробы → контроллер EndpointSlice добавляет готовые поды в список адресов сервиса.

</details>

<details>
<summary><b>Карта</b> — знать, что это существует</summary>

- Под нельзя изменить или перенести — только заменить; DaemonSet, Job, CronJob для другой работы → «раздел Под и контроллеры».
- Сервис — имя поверх списка адресов по меткам; по умолчанию открыто всё, закрывают NetworkPolicy; права пода — RBAC → «раздел Сервис».
- readiness решает, слать ли запросы; liveness перезапускает; startup откладывает обе → «раздел Пробы».
- Выкат задают `maxSurge`, `maxUnavailable` и условие готовности; `rollout status` ждёт чисел, а не ответа приложения → «раздел Выкат и откат».
- Остановка: `SIGTERM` и удаление из EndpointSlice идут наперегонки — нужны `preStop` и обработчик; PDB для плановых перерывов → «раздел Выкат и откат».
- `requests` — заявка планировщику, `limits` — потолок: процессор тормозят, память убивают; QoS, HPA → «раздел Ресурсы».

</details>

<details>
<summary><b>Подвох</b> — крайние случаи и частые ошибки</summary>

- Без readiness выкат зелёный через секунду, а приложение ещё не отвечает.
- Зависимости в liveness: упала база — перезапускаются все поды разом.
- `latest` не даёт выката; правка ConfigMap не меняет переменные и не запускает выкат.

</details>
