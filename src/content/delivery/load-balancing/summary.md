# Балансировка нагрузки и проверки здоровья

`delivery/load-balancing` · выжимка составлена с ИИ 2026-10-29 по тексту темы. Ключ ответа: сначала расскажи тему сам за 2 минуты, не глядя, потом открывай.

<details>
<summary><b>Ядро</b> — что нужно помнить</summary>

- **Что это:** прокси перед несколькими одинаковыми копиями приложения, который решает, какая копия получит запрос.
- **Зачем:** одна копия упирается в одну машину и падает вместе с ней; снаружи один адрес, внутри бэкенды можно добавлять, убирать и перезапускать.
- **Как работает:** три независимых решения: **кому** отдать (круг, веса, `least_conn`, хеш по ключу) → **кого** считать больным (активные или пассивные проверки) → **можно ли повторить** запрос на соседе (идемпотентность).

</details>

<details>
<summary><b>Карта</b> — знать, что это существует</summary>

- L4 выбирает бэкенд на соединение, L7 — на запрос; HTTP/2, gRPC и WebSocket прилипают → «раздел Соединения или запросы».
- Плавный взвешенный круг nginx перемешивает, а не шлёт пачкой; без `zone` у каждого процесса свой счёт → «раздел Круг и веса».
- `least_conn` смотрит на незаконченные запросы; при нескольких балансировщиках — «два случайных» → «раздел Кто свободнее».
- Остаток от деления тасует почти все ключи, кольцо переносит только долю нового; `ip_hash`, липкие сессии по cookie → «раздел Хеш по ключу».
- В открытом nginx только пассивные проверки; что считать отказом, решает `proxy_next_upstream` → «раздел Проверки здоровья».
- Уже ушедший `POST` не повторяется; безопасным для повтора его делает только приложение → «раздел Повторы».
- Вывод: перестать брать новые, доделать начатые, закрыть простаивающие, выйти → «раздел Плавный вывод».

</details>

<details>
<summary><b>Подвох</b> — крайние случаи и частые ошибки</summary>

- Ответ 500 для nginx не отказ: такой бэкенд остаётся в строю.
- Сбой всех разом на долю секунды даёт 502 на весь `fail_timeout`.
- `server.close()` не закрывает keep-alive, занятое в момент вызова, — вывод не кончается; нужен `Connection: close`.

</details>
