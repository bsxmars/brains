# Кеш данных на клиенте: TanStack Query и SWR

`frameworks/data-cache` · выжимка составлена с ИИ 2026-10-29 по тексту темы. Ключ ответа: сначала расскажи тему сам за 2 минуты, не глядя, потом открывай.

<details>
<summary><b>Ядро</b> — что нужно помнить</summary>

- **Что это:** стор, который сам ходит в сеть: компонент подписывается на ключ, кеш решает, идти ли на сервер.
- **Зачем:** серверные данные — копия, стареет сама и нужна многим компонентам; без кеша — дубли запросов, расходящиеся копии, ручные флаги.
- **Как работает:**
  1. Ключ-массив → строка → запись в `Map` (данные, ошибка, время, наблюдатели, промис).
  2. Запрос в пути — второй наблюдатель ждёт тот же промис.
  3. Устаревшие данные показываются, обновление идёт фоном (монтирование, фокус, сеть).
  4. После мутации приложение инвалидирует префикс ключа.

</details>

<details>
<summary><b>Карта</b> — знать, что это существует</summary>

- Две оси: «есть ли данные» и «идёт ли запрос» → «раздел Кеш по ключу».
- Срок свежести и срок хранения — разные вещи; гидратация с сервера → «раздел Свежесть и сборка мусора».
- Обновление при фокусе и возврате сети, повторы с растущей паузой → «раздел Фокус и повторы».
- Оптимистичная запись, откат, сверка → «раздел Мутации».
- Неизменившиеся части ответа сохраняют старые ссылки → «раздел Структурное разделение».
- SWR: окно дедупликации вместо свежести, нет сборки мусора → «раздел SWR».

</details>

<details>
<summary><b>Подвох</b> — крайние случаи и частые ошибки</summary>

- По умолчанию каждое монтирование — запрос; параметр `queryFn`, не попавший в ключ, склеивает разные запросы в одну запись.
- Оптимизм без `cancelQueries` мигает: старый фоновый ответ затирает запись.
- На сервере `QueryClient` — на каждый запрос, иначе данные пользователей смешаются.

</details>

- `replaceEqualDeep`, `notifyOnChangeProps` → «раздел Структурное разделение».
- `dedupingInterval` 2 с, `focusThrottleInterval` 5 с, `errorRetryInterval` 5 с → «раздел SWR».
