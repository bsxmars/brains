  После `el.style.width = '200px'` элемент на экране не сразу станет шире. Браузеру нужно

      Они возвращают разное. `textContent` возвращает весь текст дерева, включая скрытый, — это
      чистая работа с DOM. `innerText` возвращает **то, что видит пользователь**: с учётом
      `display: none`, схлопнутых пробелов и переносов. Чтобы это узнать, нужна геометрия.

      <CardNote tone="warn">

        Если нужен исходный текст узла, берите `textContent`. Если нужен текст с учётом
        раскладки, `innerText` решает другую задачу. После записи, меняющей геометрию,
        такое чтение может потребовать синхронный layout.

  Когда элементы измеряют и меняют разные компоненты, их операции тоже могут чередоваться.
  Поэтому порядок согласовывают для всей страницы: сначала выполняют измерения, затем меняют
  DOM и стили.

  <Disclosure title="Пример общего планировщика чтений и записей">

    Чтение и запись выполняются в разных компонентах, которые ничего не знают друг о друге. Компонент A
    измеряет контейнер, компонент B ставит высоту, компонент C снова измеряет — и вместе они дают
    то же чередование, хотя каждый по отдельности написан правильно. Нужно **одно место
    на всю страницу, где сначала собираются все чтения, затем все записи**. `rAF` даёт
    такую общую точку перед плановым layout. Первое чтение всё ещё может потребовать пересчёт,
    если DOM был изменён раньше; такой порядок избавляет от повторных пересчётов, но не делает любое чтение бесплатным.

    <CodeBlock code={RAF_BATCH_CODE} size={11.5} lh={1.7} pad="15px 17px" />

    <CardNote tone="prose">

      **У приёма есть цена.** Чтение, поставленное в очередь из записи, выполнится в следующем
      кадре. Код вида «изменил размер → сразу измерил» не получит ответ синхронно
      в текущей задаче. Если ответ нужен сразу, один принудительный пересчёт допустим.
      Повторение такого пересчёта на каждой итерации может заметно замедлить цикл.

    </CardNote>
  </Disclosure>
