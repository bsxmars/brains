# Пакетные менеджеры

`tooling/package-managers` · выжимка составлена с ИИ 2026-10-29 по тексту темы. Ключ ответа: сначала расскажи тему сам за 2 минуты, не глядя, потом открывай.

<details>
<summary><b>Ядро</b> — что нужно помнить</summary>

- **Что это:** инструмент, превращающий диапазоны из `package.json` в конкретные архивы на диске.
- **Зачем:** `package.json` описывает, что подошло бы, а не что стоит; загрузчик Node его не читает — какую копию получит `require`, решает раскладка.
- **Как работает:** под каждый диапазон берётся старшая подходящая версия; npm поднимает её как можно выше в `node_modules` (порядок — по алфавиту и истории); lock-файл фиксирует версии, раскладку, адрес и хеш; pnpm кладёт наверх только объявленное, остальное — ссылками из хранилища.

</details>

<details>
<summary><b>Карта</b> — знать, что это существует</summary>

- Любой диапазон разворачивается в «от» и «до»; в `0.x` каретка сдвигается; пререлиз надо назвать поимённо → «раздел Semver и диапазоны».
- Подъём даёт фантомы и одинаковые копии; дерево npm зависит от порядка установки → «раздел Разрешение и подъём».
- `npm ci` — lock-файл как закон, `npm install` его правит → «раздел Lock-файл».
- Peer — одна копия на всех; npm при конфликте отказывает, pnpm ставит с предупреждением; `overrides` приказывает → «раздел Peer и overrides».
- Хранилище pnpm по хешам файлов, клоны или жёсткие ссылки; Yarn PnP без `node_modules` → «раздел pnpm и Yarn PnP».
- Одобрение скриптов, порог возраста версий, `npm audit` — разные рубежи захвата → «раздел Скрипты и цепочка поставок».

</details>

<details>
<summary><b>Подвох</b> — крайние случаи и частые ошибки</summary>

- Удалили lock-файл — фантом сменил мажор без правки кода.
- `--legacy-peer-deps` и `overrides` прячут конфликт, а не решают.
- npm по умолчанию предупреждает о `postinstall` уже после его выполнения.

</details>
