# Безопасность бэкенда глазами фронтенда

`platform/backend-security` · выжимка составлена с ИИ 2026-10-29 по тексту темы. Ключ ответа: сначала расскажи тему сам за 2 минуты, не глядя, потом открывай.

<details>
<summary><b>Ядро</b> — что нужно помнить</summary>

- **Что это:** проверки, которые живут в обработчике сервера (в том числе BFF): кто спрашивает, его ли объект, какие поля можно менять, куда сервер пойдёт по просьбе.
- **Зачем:** сервер не знает, какие кнопки показал интерфейс, — любой запрос может прийти из `curl`.
- **Как работает:** проверка стоит там, где решение исполняется:
  - владелец — в запросе к базе (`WHERE id = ? AND owner_id = ?`);
  - адрес исходящего запроса — в `lookup` соединения;
  - поля — в схеме перед записью; текст ошибки — на выходе из обработчика.

</details>

<details>
<summary><b>Карта</b> — знать, что это существует</summary>

- IDOR: одна функция доступа на все обработчики, чужое и несуществующее — одинаковый 404 → «раздел Чужой объект по id».
- SSRF: проверять не строку, а каждый IP после резолва; DNS rebinding; редирект — новый адрес → «раздел Запрос на адрес пользователя».
- SQL, HTML, оболочка: значение передаётся отдельно от текста → «раздел Инъекции».
- Массовое присваивание и prototype pollution через `__proto__` → «раздел Лишние поля».
- Ошибки без стека с `requestId`; секрет попадает в бандл значением → «раздел Ошибки и секреты».
- Серверная зависимость работает с правами процесса; проверка lock-файла в CI → «раздел Цепочка поставок».

</details>

<details>
<summary><b>Подвох</b> — крайние случаи и частые ошибки</summary>

- Middleware знает про вход, но не про объект, и его обходят; Server Actions вызываются прямым POST.
- Проверить IP заранее и вызвать `fetch` — он резолвит заново; `fetch` сам идёт по редиректам.
- `execFile` с `shell: true` снова даёт оболочку; `ORDER BY ?` молча не сортирует; zod молча отбрасывает лишние ключи.

</details>
