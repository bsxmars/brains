# Хранилища браузера

`platform/browser-storage` · выжимка составлена с ИИ 2026-11-12 по тексту темы. Ключ ответа: сначала расскажи тему сам за 2 минуты, не глядя, потом открывай.

<details>
<summary><b>Ядро</b> — что нужно помнить</summary>

- **Что это:** шесть мест для данных — куки, `localStorage`, `sessionStorage`, IndexedDB, Cache API, OPFS; для обычных вкладок доступны в области origin, sessionStorage — ещё и вкладки. В iframe возможен дополнительный раздел по верхнему сайту; куки имеют собственные правила области.
- **Зачем:** выбирают по правилам, а не по объёму: что можно положить, синхронно ли, кто видит, есть ли в воркере. Любое может оказаться пустым: серверные данные восстанавливают с сервера, локальным документам нужны экспорт или резервная копия.
- **Как работает:**
  - `localStorage` синхронный, только строки — для пары значений, нужных сразу.
  - IndexedDB асинхронная, хранит объекты; транзакция фиксируется сама, когда неактивна и запросов нет.
  - Запросы добавляют в задаче создания и её микрозадачах, либо при обработке результатов IDB. Продолжение после внешнего события не получает активность даже при живой транзакции.

</details>

<details>
<summary><b>Карта</b> — знать, что это существует</summary>

- Куки читает сервер, остальные пять он не видит → «раздел Что где хранить».
- Событие storage приходит другим документам, использующим ту же область localStorage; `sessionStorage` — своё у вкладки, копия при `window.open` → «раздел localStorage и sessionStorage».
- Схему меняют только в `onupgradeneeded`; старая вкладка без `close()` даёт `blocked` → «раздел IndexedDB».
- Необработанная ошибка запроса откатывает транзакцию целиком; `preventDefault()` спасает → «раздел Жизнь транзакции».
- Cache API: сопоставление — URL, метод и Vary ответа, срока годности нет; OPFS с синхронным доступом только в воркере → «раздел Cache API и OPFS».
- Вытеснение origin целиком, `persist()` — просьба, инкогнито стирает всё при закрытии → «раздел Квота и вытеснение».

</details>

<details>
<summary><b>Подвох</b> — крайние случаи и частые ошибки</summary>

- В нашем await fetch следующий put бросает TransactionInactiveError; первая запись успела зафиксироваться. Это не команда закрытия транзакции: причина — продолжение вне её активного момента. Сеть — до транзакции или между двумя.
- В показанной обёртке await запроса IDB и готового промиса сохраняет возможность поставить следующий запрос; это не обещание для любого промиса.
- `setItem(key, obj)` молча пишет `"[object Object]"`; при переполнении `setItem` бросает — оборачивать в `try`.

</details>
