# REST, GraphQL и gRPC-web

<details>
<summary><b>Ядро</b> — что нужно помнить</summary>

- **Что это:** три договорённости поверх HTTP: кто выбирает форму ответа, сколько запросов нужно экрану, в каком виде едут байты.
- **Зачем:** от этого зависят кеш, ошибки и нагрузка на базу; каждый способ переносит сложность в своё место.
- **Как работает:**
  - REST: ресурс на адрес, поля решает сервер, клиент склеивает экран — водопад, зато HTTP-кеш работает сам.
  - GraphQL: один адрес, исполнитель обходит запрос и вызывает резолверы; ответ повторяет форму запроса.
  - gRPC-web: схема `.proto`, protobuf с номерами полей вместо имён, статус — последним кадром тела, через прокси.

</details>

<details>
<summary><b>Карта</b> — знать, что это существует</summary>

- Under- и over-fetching REST; водопад лечат `include` или BFF ценой множества адресов кеша → «раздел REST и кеш».
- Второй заход: REST берёт из кеша, POST GraphQL — нет → «раздел REST и кеш».
- Нет резолвера — берётся свойство; порядок ключей — из запроса → «раздел GraphQL изнутри».
- N+1 и загрузчик, копящий ключи до конца тика → «раздел N+1 и DataLoader».
- Persisted queries, глубина как DoS, ошибки при 200 → «раздел GraphQL на проводе».
- Varint, трейлеры, зачем браузеру прокси → «раздел gRPC-web».

</details>

<details>
<summary><b>Подвох</b> — крайние случаи и частые ошибки</summary>

- Общий DataLoader на сервер отдаёт чужие данные — создавать на каждый запрос.
- `response.ok` у GraphQL ничего не значит, проверять `errors`; `!` уносит null выше — пропадают целые заказы.
- Automatic persisted queries не защищают: нужен список разрешённых запросов (trusted documents).

</details>
