# Стек, пакеты, команды и ловушки

> Вынесено из `AGENTS.md` 2026-10-01 дословно. Правила здесь в силе; выжимка — в `AGENTS.md`.

## Стек

Astro 7 (MDX, пререндер, острова) · Vue 3 для интерактива · `@ilomee/aura-*` 1.0.3 ·
d3-модули для графиков · Vitest · Playwright. Node ≥ 22.

**Пакеты только для тестов тем** (devDependencies, в браузер не едут; 2026-09-29):
`react-server-dom-webpack` 19.3.0 (+ `webpack` как peer) — «Server Components»; `svelte`,
`babel-plugin-react-compiler` + `@babel/core@7`, `babel-preset-solid` + `solid-js` —
«Компиляторы фреймворков»; `vue-vapor` — «Vapor Mode»; `happy-dom` — DOM в Node.

⚠️ **`vue-vapor` — это алиас `npm:vue@3.6.0-rc.9`, а не отдельный пакет.** Сайт живёт на Vue 3.5,
Vapor есть только в 3.6, а поднять весь сайт на RC ради одной темы нельзя. Алиас кладёт 3.6
рядом: его `@vue/*` лежат вложенно в `node_modules/vue-vapor/node_modules/`, верхние `@vue/*`
остаются 3.5.42. Отсюда два правила: импортировать 3.6 **только явными путями** из
`node_modules/vue-vapor` (голое `@vue/runtime-vapor` из корня не разрешится или найдёт не то) и
в тесте проверять загруженную версию. И `react-server-dom-webpack/server` без условия
`react-server` бросает при импорте — он живёт в отдельном процессе `node --conditions=react-server`.

⚠️ **Svelte и Solid в Node по умолчанию отдают серверную сборку — без реактивности.** Условие
`default` у `svelte` ведёт на серверный `mount`, условие `node` у `solid-js` — на SSR-сборку, где
сигналы не обновляют ничего. Тест, запущенный «как есть», покажет застывший компонент и сойдёт
за находку. Лечение: `svelte/src/index-client.js` по абсолютному пути, у Solid — подмена
разрешения имён на `dist/solid.cjs` и `web/dist/web.cjs` (`tests/unit/framework-compilers.test.ts`).
И ловушка исполнения вывода Svelte: `$.delegate([...])` стоит **после** `export default function`;
превратите экспорт в `return` — делегирование не зарегистрируется, и клики молча не дойдут.

⚠️ **Текст ошибки React сверяют в той сборке, которую видит читатель.** `react-server-dom-webpack/client.browser`
в продакшене пишет `Minified React error #441`, а `client.node` — полную фразу; проверка только
в Node покажет не то, что увидит браузер. Отладочный поток Flight от прогона к прогону разный
(строки `J` то есть, то нет) — утверждать можно только устойчивые строки. Порядок кусков потока
в тесте задаётся «базой», отвечающей через N оборотов `setImmediate`, а не таймером — тогда он
не зависит от нагрузки (`tests/unit/server-components.test.ts`).

⚠️ **Число, которое меняется от `npm install`, в текст не пишут.** «Прогнано по lock-файлу курса:
650 пакетов» покраснело в тот же день, когда поставили пакеты для трёх новых тем (стало 736) —
тест ловил установку, а не ошибку. В тексте теперь «сотни пакетов», тест держит порядок величины
и «ноль замечаний» (`backend-security`).

⚠️ **`MutationObserver` в happy-dom сравним между фреймворками только по `characterData`.**
Замена `textContent` даёт число записей `childList`, зависящее от реализации DOM, а не от
фреймворка. JSX для исполнения в тестах снимается `typescript.transpileModule` с `jsx: react-jsx` —
`@babel/plugin-transform-react-jsx` в проекте нет.

```bash
npm run dev              # дев-сервер
npm run build            # сборка
npm run check            # типы (astro check)
npm test                 # vitest: примеры уроков и логика
npm run e2e              # playwright: палитра, шрифты, раскладка
npm run lint             # eslint: границы слоёв и шов к библиотеке
npm run legacy:extract   # перераспаковать оригиналы (после правок в JS/)
```

⚠️ **`astro dev` и `astro preview` в Astro 7 — демоны.** `npm run dev` запускает фоновый
процесс и завершается сам, поэтому «убил npm — убил сервер» здесь неверно: управлять надо
через `npx astro dev status | logs | stop` (и так же для `preview`).

Отсюда же две ловушки:

- **смена схемы коллекции подхватывается только при перезапуске** — правка текста в MDX едет
  на лету, а новое поле во frontmatter нет: данные лежат в `.astro/`. Симптом — страница
  показывает прежний вариант, сколько ни перезагружай вкладку. Лечение: `npx astro dev stop`,
  `rm -rf .astro`, снова `npm run dev`;
- **Playwright нельзя вешать на `webServer`** — команда завершается мгновенно, и он считает
  сервер упавшим. Сборка и запуск живут в `tests/e2e/global-setup.ts`;
- **демон один на проект, и свой предпросмотр мешает прогону.** `global-setup` поднимает
  предпросмотр на порту 4329; если вы уже держите свой — для скриншотов, например, — второй
  не поднимется, и прогон упадёт на «сервер предпросмотра не поднялся», не дойдя до тестов.
  Гасите свой (`npx astro preview stop`) перед `npm run e2e`.

⚠️ **`astro check` не разбирает шаблоны `.vue` — там типы не проверяет никто.** Проверено:
`npm run check` даёт 0 ошибок на 340 файлах, а `npx vue-tsc --noEmit` на том же дереве находит
пять давних ошибок в шаблонах — `defaulting-lab`, `procedure`, `rules-builder` и `self-check`.
Их не ловит ни проверка типов, ни сборка: Vue-шаблон компилируется в рантайме, а `astro check`
смотрит только скриптовую часть. Дыра особенно широка у виджета, который **никуда ещё не
импортирован**: его шаблон в этот момент не разбирает вообще ничто.

**Закрыто 2026-09-29: `npm run check` = `astro check && vue-tsc --noEmit`.** Перед этим дерево
вычищено до нуля: последняя из давних ошибок оказалась настоящей — в `self-check` кнопки
«подсказка» и «показать разбор» молча не работали (шаблон разворачивал `Ref`, та же ошибка, что
в `procedure` ниже). Краснота сторожа доказана: возврат `toggle(hinted, i)` в шаблон даёт выход 2
и `TS2345` на этой строке. Цена — `check` дольше на полный проход `vue-tsc`.

⚠️ **Запись в реактивную величину из функции-`ref` вешает страницу — и молча.** Поймано
в `widgets/defaulting-lab`: узлы собирались в шаблоне через `:ref="(el) => setCell(el, kw.key)"`,
а `setCell` читал и тут же записывал `cells`, объявленный как `ref`. Функция-`ref` вызывается
на каждом рендере, значит компонент писал в величину, которую сам же прочитал во время рендера:
render-эффект инвалидировался собственной записью и уходил в бесконечный цикл.

Опасна здесь не сама ошибка, а её тишина. **Предупреждение Vue «Maximum recursive updates
exceeded» живёт только в dev-сборке**, а страницы курса собраны в прод — в консоли ноль ошибок,
разметка на месте, сборка зелёная, и лишь главный поток занят навсегда. Симптом со стороны
проверок: `page.evaluate` в Playwright не возвращается до таймаута теста, а сообщение об ошибке
указывает на строку `evaluate`, то есть **не на виноватый код**. Диагностика, которая сработала:
прокручивать к разделам по одному и после каждого спрашивать страницу, отвечает ли она, — виснет
ровно на том разделе, где гидратируется виноватый остров.

Отсюда правило: **всё, что вызывается из шаблона на каждом рендере, пишет только
в нереактивное.** Собранные DOM-узлы реактивными быть не обязаны — наружу светит результат
их измерения, а не они сами.

⚠️ И следствие для проверок: `anchors.spec` кликает **четвёртый** пункт полосы. Это зависание
существовало и раньше, но тест до него не доходил — на прежнем оглавлении четвёртый пункт
приходился на другой раздел, и проверка успевала уйти в `skip` по «докручено до конца».
Появление в `nav` раздела «Перед началом» сдвинуло нумерацию на один — и вскрыло дефект.
Вывод общий: **сдвиг оглавления меняет то, что именно проверяет сторож**; зелёный прогон
до правки не означает, что проверено было то же самое.

⚠️ И мелочь, на которой легко обмануться: `npx vue-tsc --noEmit 2>&1 | tail -30; echo $?`
покажет код выхода **`tail`**, а не проверки. Судить надо по строкам с ошибками, а не по нулю.

⚠️ **Пока идёт работа над темой, гоняют только её тесты, а полный прогон — один раз, перед коммитом.**
В наборе больше 160 файлов, среди них тяжёлые: настоящий Postgres в PGlite, Chromium, дочерние
jest и vitest, примеры с нарочно дорогими регулярками. Полный прогон после каждой правки грел
ноутбук, а при нескольких агентах разом прогоны накладывались друг на друга. Поэтому так:

```bash
npx vitest run tests/unit/<тема>.test.ts               # тест своей темы
npx vitest related src/content/<коллекция>/<slug>/data.ts  # тесты, которые импортируют файл
npx playwright test tests/e2e/<проверка>.spec.ts        # одна браузерная проверка
```

Число воркеров ограничено в конфигах: `maxWorkers: 2` в `vitest.config.ts` и `workers: 2`
в `playwright.config.ts`. По умолчанию оба запускают воркер на каждое ядро, а флаг
`--no-file-parallelism` в командной строке забывали. Не поднимайте этот предел ради скорости.

⚠️ **Замерная проверка краснеет от нагрузки, а выглядит это как находка.** `tests/unit/v8-engine.test.ts`
сверяет отношения времени, и под параллельной работой (восемь агентов разом собирали и гоняли
тесты) три его проверки упали, причём одна показала, что **полиморфный доступ дешевле
мономорфного** — физически невозможный результат. На тихой машине те же проверки дали 18 из 18
три прогона подряд. Отсюда два следствия. Первое: **прежде чем править порог, повторите
в тишине** — иначе подвинете верное число под неверный замер. Второе: у такой проверки есть
настоящая слабость — в сборочной системе, где задачи идут параллельно, она будет мигать;
лечится это не порогом, а тем, чтобы замерные файлы шли отдельно от всего остального.

⚠️ **Проверки памяти процесса мигают так же.** `node-memory.test.ts` («`rss` видит всё целиком»)
упала один раз в общем прогоне: `rss` 283 МБ при 300 МБ буферов — под нагрузкой macOS сжимает
страницы, и резидентная память оказывается меньше выделенной. Отдельно тот же тест прошёл 3/3.
Прежде чем чинить такое сравнение, повторите его в тишине.

⚠️ **Доказывая, что тест умеет краснеть, проверьте, что правка вообще применилась.** Приём
«сломай утверждение, убедись, что упало, откати» — обязательный, но у него есть тихий отказ:
редактирование может не примениться, прогон останется зелёным, и «доказательством красноты»
окажется несуществующая правка. Поймано на `tests/e2e/security-cookies.spec.ts`: `perl -0pi`
молча не тронул файл, тест прошёл, и вывод «сторож не краснеет» был бы ложным вдвойне.
Лечение простое: после наложения правки **перечитайте место** (`grep` по новому тексту) и только
потом запускайте. Это частный случай общего правила этого файла: инструмент, отчитавшийся
об успехе, ещё не сделал работу — за сессию так соврали регулярное выражение по разделам,
три детектора React и счётчик кода выхода.

⚠️ **Отчёт `vitest` — один файл на проект, и одновременные прогоны затирают его друг другу.**
`.vitest/json/output.json` общий. Два прогона разом — и «проверка устойчивости» читает чужой
отчёт: зелёное показано, но про чужие тесты. Ловушка коварна тем, что выглядит как успех,
а не как сбой. Поймано на том, что работу разобрали по нескольким исполнителям сразу; если
прогонов может быть больше одного, каждый обязан писать отчёт в собственный файл.
⚠️ Флаг `--outputFile=<файл>` один файла не пишет — нужен ещё `--reporter=json`
(`npx vitest run … --reporter=json --outputFile=…`); без него «свой отчёт» просто не появляется.

⚠️ **И вторая половина той же ловушки: при падении отчёт не перезаписывается вовсе.** Прогон
краснеет, а `.vitest/json/output.json` остаётся от **прошлого, успешного** запуска — со своим
`"success": true`. Кто судит по отчёту вместо живого вывода, получает вчерашнее зелёное.
Поймано дословно: доказательство красноты нового сторожа дважды показало «упало 0» при заведомо
сломанном контенте — правка применилась (проверено `grep`), а отчёт был часовой давности; живой
вывод на том же месте честно дал `Tests 2 failed | 247 passed`. Отсюда правило: **судить по
выводу прогона; отчёт читать только когда он заведомо от этого прогона** — например, сверив
время его записи.

⚠️ **Сборка под открытым браузером ломает съёмку.** `npm run build` и `npm run e2e` переписывают
`dist/`, из которого предпросмотр раздаёт страницы, — снимок, сделанный в этот момент, поймает
не страницу, а пустоту. Скриншоты и пересборку разводите по времени, а не по параллельным
командам: это стоило трёх потерянных съёмок за один день.
